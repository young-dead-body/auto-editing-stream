# Журнал реализации и проверки для последующего анализа

Дата проверки: 7 ноября 2026 года, UTC. Документ описывает изменения этого этапа и сохраняет конкретные результаты, чтобы следующий инженер или модель Astra могли отличить проверенное поведение от гипотез.

## Принятые решения

1. **Отбор в два этапа.** Полная запись сначала проходит дешёвый поиск по речи и громкости. Видеомодель работает только с уже выбранными интервалами CSV. Это ограничивает время работы на длинных стримах, но означает, что пропущенный первым этапом тихий визуальный момент второй этап не восстановит.
2. **Локальная модель без тяжёлого Python-зависимого пакета.** SmolVLM2 запускается как GGUF через отдельный `llama-server`. Приложение на Python общается с ним по HTTP на `127.0.0.1`, создаёт процесс только на время задания и завершает его после анализа. Это сохраняет небольшой размер основного установщика и позволяет CPU-обработку. Загрузка файлов модели и бинарного рантайма разрешена при первом запуске, затем используется кэш.
3. **Три размера модели.** 2.2B Q4 для GPU с достаточной памятью, 500M Q8 для ограниченного GPU и CPU с ≥6 ГБ доступной RAM, 256M Q8 для CPU с 4–6 ГБ. На Windows сначала пробуется Vulkan, на Linux только при наличии render-device, на Mac Apple Silicon — Metal. Неудачный старт GPU ведёт к CPU. Реальные VRAM/RAM требования зависят от числа кадров и сборки `llama.cpp`, поэтому выбор проверяется запуском, а не только расчётом.
4. **Проверяемый результат.** Модель возвращает три оценки 0–4, описание события и наблюдаемые признаки. Ответ ограничен JSON Schema и валидируется ещё раз в Python. Формула релевантности фиксирована и документирована; при низкой уверенности итог ограничен 49. Подробный отчёт и кадры сохраняются рядом с CSV. Все результаты 256M и ответы с объяснением короче трёх слов получают `low_confidence`.
5. **Сохранение редакторской работы.** Глубокий анализ не меняет границы, категорию, причину, старый `score` 1–5 или флаг ручной проверки. Добавляется `relevance` 0–100. UI сортирует только отображение, CSV остаётся в прежнем порядке. Новый таймкод инвалидирует отчёт, изменение причины сохраняет его.

## Артефакты и совместимость

Старые CSV с шестью колонками по-прежнему читаются. После глубокого анализа добавляется седьмая колонка `relevance`; XML и MP4-экспорт читают используемые ими старые колонки. Дополнительные файлы: `.visual.json`, `.visual-progress.json`, `.visual-frames/`, `.stats.json`. Их схема и семантика описаны в `VISUAL_ANALYSIS.md`. Все данные, включая скачанные модели, хранятся локально в папке данных приложения. Windows-установщик использует `%LOCALAPPDATA%\StreamEditor`; Docker — `/data/stream-editor`; путь можно переопределить `STREAM_EDITOR_DATA`.

Важная миграционная особенность: `score` и `relevance` имеют разные шкалы и разный смысл. `score` 1–5 сохраняется ради совместимости и ручного редактирования. `relevance` 0–100 — сортировочный балл по текущей формуле, а не вероятность популярности. Не обучайте порог публикации на его абсолютном значении до калибровки на реальных примерах.

Синтетический ролик показывал тестовую картинку, а не игру. Значение `relevance=0` и пустое объяснение у 500M в этой проверке нельзя считать оценкой качества игровых клипов. Такой ответ помечен `low_confidence`. Тесты Windows и macOS добавлены в CI, но в локальной Linux-среде не были запущены. GPU-инференс также не проверялся локально из-за отсутствия подходящего устройства. Дополнительная проверка 2.2B Q4 на CPU показала корректный запуск и ответ на кадрах 512×384, но на синтетических кадрах она выдумала `game_event`. Поэтому промпт усилен требованием назвать конкретное видимое изменение, версия промпта поднята до 2, а оценка с бессодержательным объяснением ограничена 49. Повторный запрос 2.2B с промптом версии 2 вернул `event=0`, `event_type=static` на том же синтетическом видео. Запрос с восемью кадрами 512×384 уложился в контекст 8192 токенов и также вернул `event=0`. Запрос к исходному изображению 5184×3456 превышал контекст 8192 токенов; рабочий путь использует кадры шириной 512 пикселей.

## Проверка публикации v0.1.0

Коммит 01485159339065ea7936fd252bf100ed28211bcd отправлен в main и помечен тегом v0.1.0. Запуск GitHub Actions 42374881121 собрал macOS и Linux amd64, но Windows job завершился ошибкой на шаге проверки упакованной задачи глубокого анализа. Предыдущие проверки Windows — запуск страницы, XML, транскрибация с моделью tiny, быстрый анализ и экспорт клипа — прошли. Упакованная задача deep_analysis.py не завершилась за 120 секунд; job.log остался пустым, а диагностическая ветка diagnostics/windows-v0.1.0 сохранила список процессов с активным StreamEditor.exe. Из этого нельзя заключить, что причина в логике оценки: процесс не дошёл до записи диагностического сообщения. Релиз v0.1.0 не был опубликован, потому что job публикации зависит от всех платформенных проверок.

Для следующего запуска лимит ожидания этого шага увеличен до 300 секунд; при повторном таймауте job выведет PID, родительский PID, командную строку и содержимое лога. Положительный исход подтвердит, что задержка была связана с запуском на Windows runner; повторная ошибка потребует анализа процесса и bootloader PyInstaller. Проверка по-прежнему требует завершения задачи с ошибкой об отсутствующем CSV, подтверждающей загрузку упакованного скрипта.

## Контрольные точки для Astra

- Проверить на реальных игровых записях, что 1 кадр/с и максимум 8 выбранных кадров захватывают короткие победы, поражения, столкновения и реакции. Для пропусков измерить отдельно долю ошибок быстрого отбора и долю ошибок визуальной модели.
- Разметить минимум несколько десятков положительных и отрицательных моментов из разных игр и стримеров. Считать precision@5/10, recall событий и согласие редактора с `relevance`; сравнить 500M и 2.2B на одних и тех же фрагментах.
- Проверить, что текст `evidence` действительно описывает показанные кадры. На 256M реальный тест показал пустое/бессмысленное объяснение даже при корректном JSON. Возможные улучшения: отдельный запрос на описание кадра, затем отдельная классификация; увеличение модели; специализированные промпты по жанрам игр. Веса формулы менять только после появления измерений.
- Измерить пиковую RAM/VRAM, время загрузки и время на интервал для Windows CPU/Vulkan, Linux CPU/Vulkan и Mac Metal. По результатам уточнить пороги 4/6 ГБ, число кадров и `ctx-size=8192`.
- Проверить Windows-артефакт на машине без Python и с разными GPU-драйверами. Платформенный smoke test в CI выявит ошибки запуска CPU-бинарника, но не заменит тест Vulkan/Metal на реальном устройстве.
- Сохранить версии GGUF, `mmproj` и `llama.cpp` как единую совместимую тройку. При обновлении модели, промпта, структуры кадров или формулы поднять `PROMPT_VERSION` и добавить миграционный тест отчёта, чтобы старый кэш не выдавался за новый результат.
